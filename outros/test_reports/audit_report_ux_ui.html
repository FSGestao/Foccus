Problemas Detalhados

Cada problema com passos para reproduzir, evidência, impacto e recomendação. Clique para expandir.

#001 Ausência total de feedback visual
P0 Sev 4 Baixo
▶
Categoria
UX / Usabilidade
Tela / Fluxo
Todas as telas — criar, editar, excluir tarefa/projeto/pessoa
Passos para reproduzir
  1. Criar uma tarefa via quick add ou modal
  2. Alterar status, prioridade ou prazo de uma tarefa
  3. Excluir uma tarefa (após confirm)
Comportamento observado
Nenhum feedback visual (toast, animação, snackbar). A ação é executada silenciosamente. Em caso de falha do localStorage, o usuário não é notificado.
Comportamento esperado
Toast/snackbar confirmando "Tarefa criada ✓", "Status alterado para Em andamento", "Tarefa excluída — Desfazer" etc.
Impacto
Usuário não sabe se a ação foi executada com sucesso. Incerteza constante na operação.
Evidência
Nenhuma chamada a componente de feedback em updateTask(), submitNewTaskInternal(), deleteTask().
Recomendação
Implementar sistema de notificações toast com auto-dismiss (3s). Mensagens contextuais para cada ação. ~2h de trabalho.
#002 Uso de prompt() e confirm() nativos do navegador
P0 Sev 3 Médio
▶
Tela / Fluxo
Criar projeto, criar pessoa, editar pessoa, renomear projeto, excluir tarefa/projeto/pessoa, alterar nome
Comportamento observado
Diálogos nativos do navegador são usados para TODAS operações de input e confirmação destrutiva. Impossível adicionar campos ricos, validação ou preview.
Impacto
UX incoerente com o design system. Criar projeto não permite definir prazo, status, prioridade ou cor. Em mobile, experiência especialmente ruim.
Evidência
addProject() usa prompt('Nome do novo projeto:'). addPerson() usa 2 prompts sequenciais. deleteTask() usa confirm().
Recomendação
Substituir TODOS os prompt/confirm por modais customizados integrados ao design system, com campos adequados e validação.
#003 Sem undo/redo após ações destrutivas
P0 Sev 4 Médio
▶
Comportamento observado
Exclusão de tarefa/projeto/pessoa é irreversível. tasks.filter(t => t.id !== id) remove permanentemente. Sem undo, lixeira ou soft-delete.
Impacto
Perda acidental de dados irreversível. Um clique errado pode destruir informações críticas do projeto.
Recomendação
Soft-delete com status 'DELETED' + toast com "Desfazer" por 5-10 segundos. Tarefas excluídas filtradas da exibição mas recuperáveis.
#004 Navegação escondida em menu drawer
P1 Sev 3 Médio
▶
Comportamento observado
Toda a navegação (7 vistas) está em um drawer overlay. Cada troca de vista requer: abrir menu → clicar vista. +1 clique a cada operação. Vista ativa não indicada no header.
Impacto
Dezenas de cliques extras por dia. Usuário perde noção de onde está na aplicação.
Recomendação
Sidebar permanente em viewport >1024px com collapse. Menu drawer apenas em mobile. Indicador de vista ativa no header.
#005 Ausência de sistema de comentários
P0 Sev 4 Alto
▶
Comportamento observado
O drawer tem "Descrição", "Anotações", "Checklist", "Histórico" — mas nenhum sistema de comentários para comunicação de equipe. O modelo de dados não tem array de comments.
Impacto
Em sistema B2B de gestão de projetos, comunicação contextual sobre tarefas é fundamental. Equipes forçadas a usar canais externos.
Recomendação
Implementar comentários com timeline, autor, data/hora, edição e exclusão.
#006 Dados armazenados apenas em localStorage
P0 Sev 4 Alto
▶
Comportamento observado
Todo o estado é armazenado em localStorage('pauta_app_state_v1'). Sem backend, API, banco de dados, autenticação ou sincronização. Limite ~5-10MB.
Impacto
Perda total ao limpar cache. Sem multi-dispositivo. Sem colaboração. Impossível uso corporativo real.
Recomendação
Backend com API REST ou Firebase. Medida intermediária: export/import JSON + indicador "Dados salvos localmente".
#007 renderVals() monolítico — recalcula tudo
P1 Sev 3 Médio
▶
Comportamento observado
renderVals() (~500 linhas) calcula TODAS as vistas (lista, kanban, waiting, calendar, stats, projetos, pessoas) a cada setState(). Cada keystroke na busca dispara recálculo completo.
Impacto
Com 100+ tarefas, delay perceptível. Com 1000+, inutilizável. buildRow() cria closures novas a cada render (pressão GC).
Recomendação
Early-returns por vista ativa. Memoizar cálculos caros. Debounce na busca (300ms).
#008 Status da tarefa não visível na lista principal
P1 Sev 3 Baixo
▶
Comportamento observado
Na lista, apenas ⏳ (Aguardando) e ⛔ (Bloqueada) têm indicação visual. "A Fazer" e "Em andamento" são indistinguíveis. Status real requer abrir drawer.
Impacto
Impossível scanear rapidamente a lista e identificar o estágio de cada tarefa.
Recomendação
Badge compacto de status na row (ex: "Em andamento" em azul, "A Fazer" em cinza).
#009Ausência total de atalhos de teclado
P1Sev 3Médio
▶
Comportamento observado
Nenhum atalho de teclado (exceto Enter em inputs). Sem /, Ctrl+K, Escape, N, J/K, Ctrl+Z.
Recomendação
Sistema de atalhos com overlay de referência. Priorizar: Escape, / para busca, N para nova tarefa.
#010Nenhuma media query — responsividade precária
P1Sev 3Médio
▶
Comportamento observado
Zero @media queries. Responsividade depende de min(), flex e overflow-x:auto. Sem tratamento para mobile: fontes, touch targets, layout.
Recomendação
Breakpoints para tablet (768px) e mobile (480px). Reorganizar header, stack filtros, aumentar touch targets.
#011Sem loading states em nenhuma operação
P1Sev 3Baixo
▶
Comportamento observado
Nenhum estado loading, spinner ou skeleton. Botões não desabilitam durante processamento. Preparação para backend inexistente.
Recomendação
Loading states nos botões de submit + disabled state durante operações.
#012Contraste insuficiente em textos secundários
P1Sev 3Baixo
▶
Comportamento observado
--pb-text-dim com opacidade 38-40% produz contraste ~2.3-3.0:1. WCAG AA exige 4.5:1 para texto normal.
Recomendação
Aumentar opacidade para 0.55+ (claro) e 0.50+ (escuro). Alterar 2 valores no themeTokens().
#013Sem drag-and-drop no Kanban
P1Sev 3Alto
▶
Comportamento observado
Cards do Kanban não suportam arraste. Para mover entre colunas, precisa abrir drawer e alterar select. O Kanban é apenas visualização passiva.
Recomendação
HTML5 Drag API ou SortableJS para drag-and-drop entre colunas. Essencial para valor operacional.
#014Progresso do projeto calculado incorretamente
P1Sev 3Baixo
▶
Comportamento observado
Campo progress é valor estático do seed (ex: "67%"). Concluir tarefas NÃO atualiza a barra. Indicador enganoso.
Recomendação
Calcular dinamicamente: (done / total) × 100 em renderVals(). ~10 linhas de código.
#015Foco não gerenciado em modais/drawers
P1Sev 3Médio
▶
Comportamento observado
Modais e drawers sem focus trap, sem role="dialog", sem aria-modal="true". Tab pode sair para elementos por trás do overlay.
Recomendação
Adicionar role="dialog", aria-modal="true", focus trap via JS, e handler de Escape.
#016Busca sem debounce e sem indicador de limpar
P2Sev 2Baixo
▶
Comportamento observado
Cada keystroke dispara re-render completo. Sem botão "×" para limpar. Sem contagem de resultados. Sem highlight do termo.
Recomendação
Debounce de 200-300ms + botão limpar + contagem de resultados.
#017Filtros não incluem projeto nem responsável
P2Sev 2Médio
▶
Comportamento observado
Quick filters apenas: P1, Aguardando, Bloqueadas, Atrasadas. Sem filtro por projeto específico, pessoa ou range de datas.
Recomendação
Dropdowns de filtro por projeto e por responsável na barra de filtros.
#018Data hardcoded no sidebar
P3Sev 1Baixo
▶
Comportamento observado
"17 de agosto de 2026" fixo na linha 133 do HTML. Não atualiza com data real.
Recomendação
Renderizar data dinamicamente em renderVals(). ~15min.
#019Toggle de subtarefas inconsistente
P2Sev 2Baixo
▶
Comportamento observado
Lista não agrupada: botão com fundo e borda, texto ▼/▶. Lista agrupada: botão transparente sem borda, SVG colorido. Estilos diferentes para mesma função.
Recomendação
Unificar componente usando um único estilo (preferencialmente SVG).
#020Calendário mostra apenas 4 dias fixos
P2Sev 2Alto
▶
Comportamento observado
Mostra apenas hoje + 3 dias. Sem navegação. Inclui eventos hardcoded. Tarefas com prazo em D+4 ou mais não aparecem.
Recomendação
Calendário navegável com visão semanal. Remover eventos hardcoded.
#021Prioridade depende exclusivamente de cor
P1Sev 3Baixo
▶
Comportamento observado
Ícone ⚑ idêntico para P1-P4. Diferenciação puramente cromática. 8% da população masculina é daltônica.
Recomendação
Adicionar texto descritivo ou ícones distintos por nível de prioridade.
#022localStorage síncrono a cada mudança de state
P2Sev 2Baixo
▶
Comportamento observado
componentDidUpdate chama JSON.stringify() + localStorage.setItem() a CADA setState (incluindo busca, filtros, scroll). Síncrono no main thread.
Recomendação
Debounce de 500ms via requestIdleCallback. Separar state transitório de persistente.
#023Escape não fecha modais/drawers
P2Sev 2Baixo
▶
Comportamento observado
Nenhum modal ou drawer responde à tecla Escape. Fechamento só via "✕" ou click no overlay.
Recomendação
Event listener global para Escape que fecha drawer/modal ativo. ~10 linhas de código.

Resultado Final

Diagnóstico Geral

Avaliação por área do produto.

ℹ️
O Foccus v1.2 é um protótipo funcional com identidade visual coesa e escopo abrangente (7 vistas, Kanban, filtros, busca, ações bulk). O design é limpo e moderno. Porém, limitações arquiteturais (localStorage-only), ausência de padrões básicos de UX (sem feedback, sem undo) e problemas de acessibilidade impedem o uso como ferramenta B2B profissional. Nota: 5.5/10
UX
  • Nenhum feedback visual após ações
  • Sem undo/redo
  • Sem sistema de comentários
  • Navegação escondida em drawer
  • Sem atalhos de teclado
UI
  • Toggle subtarefas inconsistente
  • Zero media queries
  • Data hardcoded no sidebar
  • Status não visível na lista
  • Prioridade diferenciada só por cor
Performance
  • renderVals() monolítico (~500 linhas)
  • localStorage.setItem síncrono a cada change
  • Sem virtualização de lista
  • Closures criadas em cada render
  • Busca sem debounce
Acessibilidade
  • Contraste insuficiente em textos dim
  • Foco não gerenciado em modais
  • Prioridades diferenciadas só por cor
  • Emojis sem aria-hidden
  • Sem skip-link
Escalabilidade
  • localStorage como único storage (~5-10MB)
  • Sem backend/API (impossível multiusuário)
  • Sem paginação ou virtualização
  • Progresso de projeto hardcoded
  • Sem sincronização multi-dispositivo
Pontos Positivos
  • Design visual limpo e coeso
  • Sistema de cores bem estruturado
  • Escopo rico (7 vistas, Kanban, filtros)
  • Ações bulk implementadas
  • Histórico automático por tarefa
